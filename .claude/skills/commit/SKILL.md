# Commit Workflow

コミットメッセージだけを読んで「なぜこの変更が必要だったか」が分かるように書き、許可された範囲をコミットする。コードはHow、テストはWhat、コミットログはWhy、コードコメントはWhy not（別の自然な方法を採らない制約や落とし穴）を記録する。

## 実行手順

### 1. ブランチ確認

ブランチ構成は `.claude/skills/_shared/branch-strategy.md` を参照。現在のブランチと利用可能なブランチを確認する:

```bash
git branch --show-current
git branch -a
```

- 作業ブランチにいる場合: そのまま進む
- 保護ブランチ（main/staging等）にいる場合: プロジェクトの規則とユーザーの明示的な許可に従う。同じ範囲への許可を再確認しない。作業ブランチが必要な場合は`create-branch`を使う
- ブランチ戦略が存在しない場合: ブランチ作成の要否をユーザーに確認

### 2. 変更内容の確認

```bash
git status
git diff
```

### 3. コミットメッセージの作成

対象ファイルだけを`git add <files>`でステージする。ステージ後の差分を確認する:

```bash
git diff --cached
```

以下のルールに従ってコミットメッセージを作成する。

先に依頼、Issue、テスト、周辺文書と差分から変更理由を確認する。差分だけで業務上の動機や不具合を推測しない。「共通化する」などの手段や「保守性向上」だけで理由を代用せず、何を変更しやすくするのか、どの利用方法や要件に対応するのかを書く。理由が不明なら関連情報を確認し、変更の意味を左右する情報が不足する場合だけ質問する。

メッセージは会話やPRを読まずに理解することができる形にする。会話内にしか参照先がない語を具体的な機能、挙動、条件、パスへ直す。不具合と確認していない変更前の状態を欠陥として描かない。設定変更は採用する運用方針、テスト整備は固定する挙動など、確認できた目的を書く。

#### タイトルのルール

- **why中心**: 「何を変えたか」ではなく「**なぜ変えたか**」を書く。diffを見れば"what"はわかる。タイトルから「この変更の動機・目的」が読み取れること
- **体言止め**: 末尾は動名詞（`〜を追加` / `〜を修正` / `〜に対応` / `〜を改善`）で終える
- **50文字程度**: 日本語で50文字以内を目安
- **英日間スペース禁止**: `N+1クエリ`や`Userモデル`のように詰める
- **レビュープロセスに言及しない**: 「レビュー指摘の修正」「フィードバックを受けて」等は禁止。変更の動機を直接書く（`~/dotfiles/.claude/rules/communication.md`の"No review-process meta"ルール参照）

#### 本文の改行ルール（最重要）

本文の散文部分は**必ず1段落・1行で書き切る**。どれだけ長くなっても途中で改行しない。

改行してよいのは箇条書き（`- `で始まる行）の間のみ。

```
NG（途中改行あり）:
  検索結果の表示時に関連レコードを
  個別取得していたため、
  eager loadingを導入して一括取得に変更。

OK（1行で書き切る）:
  検索結果の表示時に関連レコードを個別取得していたため、eager loadingを導入して一括取得に変更。
```

理由: Gitの各種ツール（`git log --oneline`、GitHub/GitLab UI）は段落を改行で区切る。散文の途中で改行すると、表示上は別の段落として扱われ意図が壊れる。

#### パターン選択

必要な理由と変更内容を確認してから、それが伝わる形式を選ぶ。特定のパターンを優先せず、ファイル数、変更行数、単一目的かどうか、直近の使用割合では決めない:

**パターンA: タイトル + 本文 + 箇条書き** — 複数の関連変更を含み、本文に収まらない要点の列挙がある場合

```
タイトル（why中心）

背景・目的を1段落・1行で書く（ここで改行しない）

- 具体的な変更1
- 具体的な変更2
```

本文と箇条書きはどちらか一方を省略してもよい。

**パターンB: タイトル + 本文** — 背景、要件、制約、採用理由の説明が必要な変更

```
タイトル（why中心）

背景・目的・経緯を1段落・1行で書く（ここで改行しない）
```

本文の中心は変更が必要になった背景、要件、判断の理由とする。変更内容は理由とのつながりを理解するために補う。文数を固定しない。本文がタイトルの言い換えだけならWhyの不足を確認し、不足していれば補い、タイトルだけで理由まで伝わる場合に本文を省く。識別子の列挙で理由の説明を代用しない。

**パターンC: タイトルのみ** — タイトルだけで対象、変更内容、具体的な変更理由が伝わり、重要な背景や条件が失われない場合

```
タイトル（why中心、50文字程度）
```

### 3.5 日本語セルフチェック（必須ゲート）

**この照合表を出力せずに `git commit` を実行してはならない。** コミットメッセージは`-m`で渡すためファイル書き込みのチェックを通らず、機械的な検出が効かない。ここで人手の照合を必ず行い、その結果をテキストで出力すること。「確認した」という宣言だけでは完了と見なさない。

作成したコミットメッセージのタイトルと本文を1行ずつ読み、以下の観点で照合する:

- 漢語接頭辞と名詞を組み合わせた造語 -> 「〜していない」「〜でない」に言い換える
- 助詞の省略 -> 必要な助詞を補い、語の関係を明確にする
- 既存の語彙にない業務用語の造語（プロジェクトで確立済みのドメイン用語は造語として扱わない）
- CLAUDE.mdで定めた禁止語 -> 具体的なインターフェース、条件、挙動、要件に言い換える

**出力形式（必須）**: 次の表を必ず出力する。指摘がない場合も「指摘なし」と1行明記する。

続けて文章全体を照合する。冗長な反復は文を組み直し、対比に必要な反復は残す。本文がタイトルの言い換えだけならWhyの不足を確認する。理由と行為がつながらない場合は、欠けている問題や目的を確認し、単なる文の分割や理由の創作で済ませない。

| 対象行 | 元の表現 | 判定 | 修正後 |
|--------|---------|------|--------|
| タイトル | （原文） | OK / 造語 / 助詞省略 / 禁止語 | （修正案。OKなら空欄） |
| 本文1行目 | （原文） | ... | ... |
| 全体 | （重複、Whyの不足、理由と行為のつながり） | OK / 問題と該当箇所 | （修正案。OKなら空欄） |

不自然な表現があれば修正し、修正後のメッセージでコミットする。

**禁止事項**: 照合表を出力せずに「セルフチェック済み」とだけ述べてコミットに進むこと。表の出力がこのステップを完了した唯一の証拠となる。

### 4. ユーザー確認

対象ファイル、検証結果、メッセージを提示する。対象への明示的なコミット依頼や許可があれば、その範囲で実行する。許可がなければここで得る。

```bash
# パターンC
git commit -m "タイトル"

# パターンA / B（短い本文）
git commit -m 'タイトル' -m '本文（1段落1行）'

# 複雑な本文はWriteで一時ファイルへ書き、単独で実行する
git commit -F <本文ファイルの絶対パス>
```

**変更ファイル**:
- ファイル一覧

ユーザーの許可なしにコミットを実行しない。

### 5. コミット実行と後処理

ユーザーの許可後、確認済みのコミットコマンドを実行する。

`git log -1 --format=%B`と`git status --short`でメッセージと残った変更を確認する。メッセージをコマンド置換へ埋め込まず、`git add .`、`git add -A`、`--no-verify`は使わない。

`~/.claude/plans/*.md`が存在する場合、完了したTODO項目を`- [x]`に更新する。

## Troubleshooting

| エラー | 原因 | 対処 |
|--------|------|------|
| pre-commitフックがコミットを拒否する | lintエラー・secretが含まれている等 | エラーメッセージを確認して修正後に再コミット（`--no-verify`は使わない） |
