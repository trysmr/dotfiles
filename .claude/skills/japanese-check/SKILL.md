# Japanese Check

日本語の成果物を「機械チェック」と「ニュアンスチェック」の2段階で検査し、修正まで行います。

判断基準の定義元は`~/dotfiles/.claude/rules/communication.md`のNatural Japanese Wordingセクションです。このスキルはそれを実行手順に落としたものです。

## 対象の決定

依頼内容から検査対象を特定します:

| 依頼の形 | 対象 | 取得方法 |
|---|---|---|
| 「このファイルをチェック」 | 指定ファイル | そのままスクリプトに渡す |
| 「差分をチェック」「ブランチをチェック」 | 変更差分 | `git diff main... --name-only`で日本語を含み得るファイルを列挙 |
| 出力直前のドラフト | コミットメッセージ、PR本文、ドキュメント案 | ドラフト文字列を標準入力で渡す |

## Step 1: 機械チェック

バンドルスクリプトで定型違反を検出します:

```bash
# ファイル検査
python3 <スキルディレクトリ>/scripts/check_japanese.py <ファイルパス...>

# ドラフト検査（標準入力）
python3 <スキルディレクトリ>/scripts/check_japanese.py <<'EOF'
<ドラフト本文>
EOF
```

検出対象: 英日間の空白、全角矢印、漢語接頭辞と英字の混成、既知の造語、助詞を省いた複合名詞、言い換え推奨語、禁止語、文字化け(U+FFFD)。

スクリプトは機械判定なので誤検知があり得ます。たとえば表組みの区切りや正規表現リテラル内のマッチは違反ではありません。検出結果は必ず文脈を見て採否を判断してください。

## Step 2: ニュアンスチェック

スクリプトでは拾えない表現を、対象テキストを読んで判定します。判定の軸は「声に出して読んで自然な日本語か」です。

- **漢字接頭辞の造語**: 「未〜」「非〜」で辞書にない語を作っていないか -> 「〜していない」「〜でない」に開く
- **発明された複合名詞**: プロジェクト語彙にない名詞連結がないか -> 条件を文で書くか、実際のフラグ名・属性名を使う
- **可能動詞**: 五段活用動詞から作られた可能動詞を使っていないか -> 辞書形に「ことができる」を続ける。語尾ではなく、文脈上の意味から可能表現か判断する
- **直訳調**: 英語表現の直訳で硬くなっていないか
- **review-process meta**: コミット/PR本文に「レビューで指摘されたため」等の経緯記述がないか -> 根本の動機を直接書く
- **丁寧形の混入**: コミットタイトルが「〜しました」になっていないか -> 名詞形「〜を追加」「〜を修正」で終える
- **識別子の詰め込み**: コミット本文がバッククォート識別子だらけになっていないか -> 平文の日本語で理由を1〜2文

プロジェクト既存のドメイン用語は造語と判定しません。迷ったら対象リポジトリ内でその語をgrepし、既出なら許容します。

## Step 3: 修正の適用

- **対象がファイル**: Editで修正まで適用する。定型違反（空白除去、矢印置換）は機械的に直してよい。ニュアンス系の言い換えは前後の文が自然につながるよう文単位で書き直す
- **対象がドラフト**: 修正済みの本文を提示し、そのまま次の工程（コミット、PR作成）に使う

意図的な表現の可能性がある箇所（例: 引用文、検出パターンの説明自体）は書き換えず、報告のみに留めます。

## Step 4: 修正後の確認

修正したファイル/テキストに対してスクリプトを再実行し、違反ゼロを確認します。ファイル修正時は文字化けチェックも兼ねます（スクリプトがU+FFFDを検出します）。

報告形式:

```
日本語チェック:
- 機械チェック: N件検出 -> M件修正、K件は意図的表現のため保留
- ニュアンス: <言い換えた箇所の要約、なければ「問題なし」>
- 再実行 -> 定型違反なし
```
