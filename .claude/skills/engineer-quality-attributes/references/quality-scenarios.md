# 品質シナリオ

曖昧な品質上の期待を、条件、応答、測定、確認方法、担当まで追跡できる形へ変換する。

## 作成原則

1. 先にシステム境界、利用者、重要な利用場面、障害の影響を確認する。
2. 9特性を分類してから、優先度の高い項目をシナリオへ変換する。
3. 1つのシナリオでは、1つの主要な事象と観測可能な応答を扱う。
4. 通常時、繁忙時、障害時、攻撃時、保守時などの発生条件を具体化する。
5. 測定基準の根拠と状態を必ず記録する。
6. 対策の存在と、試験結果や実環境の観測を分ける。
7. 目標を決める担当と、実装・検証・運用を担う担当を分けてよい。

## 必須項目

| 項目 | 記載内容 | 確認する問い |
|---|---|---|
| ID | `QA-001`のような追跡用ID | 他の要件、テスト、監視から参照できるか |
| 品質特性 | 製品品質または利用時品質の特性と下位特性 | 主要な評価面を1つ選んだか |
| 対象 | 機能、データ、サービス、利用者、業務など | 境界内の何を評価するか |
| 発生条件 | 通常時、繁忙時、障害時、攻撃時、保守時など | 再現できる条件か |
| 入力・事象 | 負荷、障害、操作、攻撃、変更要求など | 何が応答を引き起こすか |
| 期待する応答 | システム、運用者、利用者に期待する振る舞い | 外から確認できるか |
| 測定基準 | 時間、割合、件数、結果、順序、状態など | 合否または傾向を判断できるか |
| 検証方法 | 自動テスト、負荷試験、復旧試験、手動評価など | 条件と応答を再現できるか |
| 観測方法 | メトリクス、ログ、トレース、利用者調査など | 継続して把握できるか |
| 担当 | 判断、実装、検証、運用の担当 | 判断と対応の持ち主が明確か |
| 根拠 | 業務要件、法令、実測、既存文書、合意など | 値と優先度の由来を追えるか |
| 状態 | 合意済み、暫定、判断待ち | 確定した内容と候補を区別したか |

複数の品質特性へ影響する場合は、主要な特性を1つ選び、関連する特性を備考またはトレードオフへ記載する。同じ事象でも期待する応答が異なる場合はシナリオを分ける。

## 優先順位

次の3軸を`高`、`中`、`低`など、組織で合意した尺度で評価する。

- 影響度: 失敗時に利用者、業務、財務、安全、法令、評判へ与える影響
- 発生可能性: 利用頻度、変更頻度、依存先、過去事例から見た起こりやすさ
- 検知の難しさ: 利用者へ影響する前にテストや監視で見つけられるか

数値スコアや掛け算を導入する場合は、既存のリスク管理方法と判断境界を確認する。尺度がない場合は独自の点数を作らず、各軸と優先理由を文章で示す。

優先順位は次の場合に見直す。

- システム境界、利用者、データ、法令が変わる
- 障害、事故、攻撃、苦情が発生する
- 実測値が想定と異なる
- 対策や依存先が変わる

## 測定値の扱い

### 情報源を分ける

| 区分 | 意味 | 例 |
|---|---|---|
| 業務上必要な値 | 利用者や業務が必要とする上限・下限 | 業務処理の締切、許容できる損失 |
| 現在の実測値 | 定義した条件で実際に測った値 | 負荷試験、監視、利用者調査の結果 |
| 技術上可能な値 | 検証環境や試作で達成可能と確認した値 | 構成候補ごとの試験結果 |
| 暫定候補 | 合意前の比較や試験に使う候補 | 根拠と有効期限を添えた仮置き |
| 判断待ち | 値または判断担当を確認できない状態 | 誰がいつ決めるかを記載 |

### 禁止事項

- 業界で一般的という理由だけで、応答時間、可用性、復旧時間などの数値を生成しない。
- 現在の実測値を、そのまま必要な目標値へ置き換えない。
- サンプル値を利用者の合意済み要件として扱わない。
- 測定条件、期間、母集団、分位点が異なる値を比較しない。
- `高速`、`十分`、`安全`、`使いやすい`のような形容だけで完了としない。

値を確認できない場合は、測定項目、測定条件、値を決める担当、必要な調査を提示し、状態を`判断待ち`にする。

## 変換例

角括弧内は現地の資料または担当者の回答で埋める。値を推測しない。

### 性能効率性

曖昧: 「検索を高速にする」

変換:

- 発生条件: `[繁忙時間帯の同時利用者数]`かつ`[検索対象データ量]`
- 入力・事象: 利用者が通常の検索条件を送信する
- 期待する応答: 結果一覧と総件数を返す
- 測定基準: p95応答時間が`[承認された上限]`以内、エラー率が`[承認された上限]`以内
- 根拠: `[業務上の待ち時間制約または利用者調査]`
- 状態: 値を確認できない間は`判断待ち`

### 信頼性

曖昧: 「障害からすぐ復旧できる」

変換:

- 発生条件: `[対象環境]`で主系の`[障害対象]`が停止する
- 入力・事象: 障害を検知する
- 期待する応答: `[縮退または切替動作]`を行い、データの整合性を確認してサービスを再開する
- 測定基準: 復旧時間と失われるデータ量を、それぞれ`[業務担当者が承認した上限]`以内にする
- 検証方法: 本番相当環境での障害試験と復旧記録
- 観測方法: ヘルス状態、切替イベント、処理失敗、データ照合

### セキュリティ

曖昧: 「管理機能を安全にする」

変換:

- 発生条件: 一般利用者として認証済み
- 入力・事象: 管理者専用操作を画面外から直接要求する
- 期待する応答: 操作を拒否し、保護対象の内容を返さず、調査に必要な事象を記録する
- 測定基準: 権限のない操作が成功しないこと、機密情報が応答とログへ出ないこと
- 検証方法: 認可テスト、応答内容の確認、ログ内容の確認

### インタラクション能力

曖昧: 「入力しやすいフォームにする」

変換:

- 発生条件: `[対象利用者]`が`[端末と支援技術]`を使う
- 入力・事象: 必須項目を誤って入力し、修正して送信する
- 期待する応答: 問題箇所、理由、修正方法を認識でき、入力済みの正しい値を保持する
- 測定基準: `[代表タスク]`の完了可否、誤りからの回復可否、支援技術での案内順
- 検証方法: 自動アクセシビリティ確認と対象利用者によるタスク評価

### 保守性

曖昧: 「変更しやすくする」

変換:

- 発生条件: `[代表的な変更要求]`を実装する
- 入力・事象: 既存の`[規則または外部連携]`へ変更を加える
- 期待する応答: 影響箇所を特定し、関連しない機能を変更せず、回帰を自動確認する
- 測定基準: 影響箇所、変更ファイル、必要なテスト、実行結果を記録し、`[組織で合意した判断基準]`を満たす
- 根拠: 変更履歴、障害履歴、チームのレビュー基準

## トレードオフ

少なくとも優先度の高いシナリオ間で、改善が別の特性を悪化させないか確認する。

| 改善する特性 | 影響を受け得る特性 | 確認例 |
|---|---|---|
| 性能効率性 | セキュリティ、保守性、正確性 | キャッシュで認可や更新反映が遅れないか |
| 信頼性 | コスト、柔軟性、保守性 | 冗長化で構成と運用が複雑にならないか |
| セキュリティ | インタラクション能力、性能効率性 | 追加認証や検査が操作完了率と応答へ与える影響 |
| 柔軟性 | 性能効率性、解析性 | 抽象化や交換可能性が追跡と最適化を難しくしないか |
| 安全性 | 操作性、可用性 | 安全停止が必要な業務まで不必要に止めないか |
| データ保持 | セキュリティ、追跡性、法令対応 | 調査に必要な期間と削除要求を両立できるか |

どちらか一方を自動的に優先せず、影響、判断者、採用理由、再評価条件を記録する。

## レビュー観点

- 9特性の分類表から優先シナリオへ追跡できるか。
- 発生条件と入力・事象を再現できるか。
- 期待する応答を利用者または外部から確認できるか。
- 測定基準に根拠と状態があるか。
- 検証方法と観測方法を混同していないか。
- 対策だけで品質を満たすと判定していないか。
- 担当と次の判断期限を示しているか。
- 関連するトレードオフを記録しているか。
