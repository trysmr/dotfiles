# Deep Review

独立したOpusのコンテキストで、指定差分と直接の経路を深く確認する。レビュー担当自身が調査し、同じ差分の確認を別のchange-reviewerへ重ねて委譲しない。

## 手順

1. 指定されたリポジトリの絶対パスを作業場所とする。指定がなければ別リポジトリを推測せず確認する。
2. 対象を確定する。指定なし・`--branch`はベースからの差分、`--uncommitted`は作業ツリーとステージ済みの差分、`--staged`はステージ済み、`--commit <hash>`は該当コミット、ファイル指定はそのファイルを対象とする。
3. ブランチ比較は`../_shared/branch-strategy.md`と現在のブランチを確認する。比較元が不明、または差分がない場合は対象を確認し、勝手に過去の履歴へ広げない。
4. 差分、確認済みの要件、直接の呼び出し元・入力・保存経路・関連テストを読む。渡された既存のレビュー結果は参考とするが、今回の深い確認の代用にはしない。
5. 下の観点で成立条件と影響を確認し、根拠付きで重大度順に報告する。編集、テスト実行、追加のスキルやsubagent起動は行わない。検証は渡された実行結果を確認し、不足をleadへ返す。

## 観点

- 動作回帰、境界値、例外系、エラー処理
- データ破壊、機密情報の露出、インジェクション、認証・認可
- 結合度、責務、既存パターン、不要な抽象化、変更容易性
- 各アサーションが守る確認済みの挙動や再発条件。不在を検証する根拠
- テストで確認できない実行条件と残リスク

## 報告と境界

指摘を先に重大度順で書く。各項目は`file:line`、成立する操作経路と条件、現象、影響、根拠、対応案を示す。会話内にしか参照先がない表現や、変更全体の要約を繰り返さない。

Critical/Highは停止条件としてleadへ返す。修正はユーザーの判断後に行い、指摘が残る間はコミット・PR作成へ進まない。指摘がない場合も「問題を検出しなかった範囲」と「検証できていない事項」を分け、レビューだけでPR作成の承認としない。

セキュリティ関連変更で最後の変更後のsecurity-reviewer結果がなければ、leadが別途その確認を行う。このfork内から追加起動しない。
