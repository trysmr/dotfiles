# Commit Workflow

現在の変更を意図が分かる日本語メッセージでコミットする。

## Workflow

1. `../_shared/branch-strategy.md` を必要に応じて確認する。
2. `git branch --show-current` で保護ブランチ上でないことを確認する。
3. `git status` と `git diff` で変更内容を読む。読んでいないファイルはステージしない。
4. 秘密情報、`.env`、認証情報、不要な生成物が含まれていないか確認する。
5. 必要なテスト、lint、formatを実行する。実行できない場合は理由を記録する。
6. `git add <files>` で意図したファイルだけをステージし、`git diff --cached` を確認する。
7. 下記のMessage Rulesに従ってメッセージを作成する。
8. 日本語セルフチェックの照合表を出力する（必須ゲート。下記参照）。
9. コミット予定ファイルとメッセージ案をユーザーへ提示し、許可を得る。
10. 許可後にコミットを実行する。本文があるメッセージはHEREDOC形式（`git commit -m "$(cat <<'EOF' ... EOF)"`）で渡す。

## Message Rules

### タイトル

- 「何を変えたか」だけでなく「なぜ変えたか」が読み取れる内容にする。
- 末尾は体言止め（`〜を追加` / `〜を修正` / `〜に対応` / `〜を解消`）。丁寧形（`〜しました`）は使わない。
- 日本語で50文字前後。
- 英語の識別子と日本語の間に半角スペースを入れない（例: `Userモデル`、`N+1クエリ`）。
- レビュープロセスに言及しない（「レビュー指摘の修正」「フィードバックを受けて」等は禁止。変更の動機を直接書く）。

### 本文の構成（最重要）

- 本文は最低2文で構成する。**1文目: 何が問題だったか・なぜ現状のままでは駄目か（過去形で書く）。2文目: どう対処するか。**
- 変更内容の言い直し1文だけの本文（「〜に変更した。」のみ等）を書いてはならない。1文で済むほど小さい変更なら本文を省略してパターンAにする。
- 1段落は必ず1行で書き切る。散文の途中で改行しない。改行してよいのは箇条書き（`- `で始まる行）の間だけ。
- クラス名・メソッド名の列挙で本文を埋めない。列挙が必要ならパターンCの箇条書きに移す。

### パターン選択

**C -> B -> Aの順で検討し、最初に条件を満たしたものを使う。** Aから考え始めてはならない。

| 検討順 | パターン | 構成 | 使う条件 |
|---|---|---|---|
| 1 | C | タイトル+本文+箇条書き | 変更ファイルが多く、本文に収まらない要点の列挙がある場合 |
| 2 | B | タイトル+本文 | 上記以外すべての既定。本文は2〜3文 |
| 3 | A | タイトルのみ | 1ファイル数行の変更で、タイトルだけで動機が完全に伝わる場合に限る |

迷ったらBにする。「Bの本文が思いつかない」はAを選ぶ理由にならない。diffを読み直して「この変更をしなかったら何が困るか」を1文目に書く。

### 例（検討順に掲載）

パターンC（複数の関連変更）:

```
ダイアログ操作のリダイレクトをturbo_stream応答に変更

turbo-frame内のダイアログフォームは成功時にリダイレクトすると、Turboが送信元フレームを遷移先に探すため表示が壊れていた。成功時はturbo_streamで一覧と詳細をまとめて更新し、Turbo以外のリクエストはリダイレクトにフォールバックする。

- 共通のレスポンス処理をconcernに集約し、各コントローラを移行
- 各操作にas: :turbo_streamの契約テストを追加
```

パターンB（バグ修正: 1文目が原因、2文目が対処）:

```
バリデーション失敗時のrenderに422ステータスを追加

Turbo Driveはフォーム送信に対する200応答を処理しないため、保存に失敗してもエラー画面が表示されず無反応になる不具合があった。Rails 7以降の標準に合わせてstatus: :unprocessable_entityを指定する。
```

パターンB（改善: 1文目が現状の欠陥、2文目が対処）:

```
一覧画面のバッジ表示で関連レコードのN+1を解消

バッジの表示判定がhas_oneの存在確認であるにもかかわらず一覧クエリでpreloadされておらず、行数分のSELECTが発生していた。一覧表示と再描画の両経路のpreloadに関連を追加する。
```

パターンA（例外: タイトルだけで動機が完全に伝わる小変更）:

```
開発seedの固定日付をCURRENT_DATE基準に変更
```

NG例（この形を出力してはならない）:

```
ダイアログ操作の応答を修正

turbo_stream応答に変更した。
```

本文がタイトルの言い直し1文だけで、なぜ変更が必要だったかが書かれていない。

## Japanese Self-Check（必須ゲート）

**照合表を出力せずに`git commit`を実行してはならない。** メッセージは`-m`で渡すためファイル書き込みのチェックが効かず、ここでの照合が唯一の検査になる。「確認した」という宣言だけでは完了と見なさない。

タイトルと本文を1行ずつ読み、以下の観点で照合する:

- 漢語接頭辞の造語（未〜/非〜と名詞の合成。例: 未充足、非終端）-> 「〜していない」「終端でない」に言い換える
- 助詞の省略（例: 「次エッジ」->「次のエッジ」、「LIKE検索」->「LIKEで検索」）
- 既存の語彙にない業務用語の造語（プロジェクトで確立済みのドメイン用語は造語として扱わない）

出力形式（指摘ゼロでも表を出力し「指摘なし」と明記する）:

| 対象行 | 元の表現 | 判定 | 修正後 |
|--------|---------|------|--------|
| タイトル | （原文） | OK / 造語 / 助詞省略 | （修正案。OKなら空欄） |
| 本文1行目 | （原文） | ... | ... |

不自然な表現があれば修正し、修正後のメッセージでコミットする。

## Guardrails

- ユーザー許可なしにコミットしない。
- `git add .`、`git add -A`、`--no-verify` は使わない。
- pre-commit hookが失敗した場合は修正して再実行する。回避しない。
