# Commit Workflow

コミットメッセージだけを読んで「なぜこの変更が必要だったか」が分かる日本語メッセージを作り、許可された範囲をコミットする。形式や短さより、変更理由が伝わることを優先する。

## 記録の役割

- コードにはHow: どう実現するか。
- テストコードにはWhat: 何が成立すべきか。
- コミットログにはWhy: なぜこの変更が必要だったか。
- コードコメントにはWhy not: なぜ別の自然な方法を採らないのか。制約や落とし穴を残す。

この役割分担を軸に、コミットログには変更の判断に至った理由を残す。変更内容や実装方法は、その理由と対応を理解するために必要な範囲で添える。コードやテストの説明を繰り返すことで、理由の説明に代えない。

## Workflow

1. `../_shared/branch-strategy.md` を必要に応じて確認する。
2. `git branch --show-current` で作業場所を確認する。保護ブランチでの作業はプロジェクトの規則とユーザーの明示的な許可に従う。
3. `git status` と `git diff` で変更内容を読む。読んでいないファイルはステージしない。
4. 秘密情報、`.env`、認証情報、不要な生成物が含まれていないか確認する。
5. 必要なテスト、lint、formatを実行する。実行できない場合は理由を記録する。
6. `git add <files>` で意図したファイルだけをステージし、`git diff --cached` を確認する。
7. 下記のMessage Rulesに従ってメッセージを作成する。
8. 日本語セルフチェックの照合表を出力する（必須ゲート。下記参照）。
9. コミット予定ファイルとメッセージ案をユーザーへ提示する。対象への明示的なコミット依頼や許可があれば、その範囲で実行する。許可がなければここで得る。
10. 許可されたコミットを実行する。短い本文はシェルで安全に引用した別の`-m`引数へ渡す。複数段落や動的な内容は一時ファイルへ書き、`git commit -F <path>`で渡す。コマンド置換へメッセージを埋め込まない。
11. `git log -1 --format=%B`と`git status --short`で、メッセージと残った変更を確認する。

## Message Rules

コミットメッセージだけを読んだ新規参加者が、何が変更の必要性を生み、その変更がどう応えるのか理解できるように書く。会話、PR、diffを読まなければ理由が分からないメッセージは書き直す。「先ほどの指摘」「今回追加したもの」「このケース」など、参照先が会話内にしかない表現は、具体的な機能、挙動、条件、パスへ直す。

### 理由を確認してから形式を選ぶ

依頼内容、issue、テスト、周辺文書と差分から、変更が必要になった背景や要件を確認する。既に確認した情報は利用する。差分は変更内容の根拠になるが、それだけで業務上の動機や不具合を推測しない。

「共通化する」「一括取得する」は手段であり、それだけでは理由にならない。「保守性向上のため」「運用に合わせるため」も、何を変更しやすくしたいのか、どの運用に対応するのかが分からなければ補う。確認できた具体的な問題、要件、制約と変更内容を結び付ける。

理由が分からない場合は関連する依頼や文書を確認し、それでも変更の意味を左右する情報が不足する場合だけ質問する。表現やパターンの選択は自分で判断する。

### タイトル

- 「何を変えたか」だけでなく「なぜ変えたか」が読み取れる内容にする。
- 末尾は体言止め（`〜を追加` / `〜を修正` / `〜に対応` / `〜を解消`）。丁寧形（`〜しました`）は使わない。
- 日本語で50文字前後を目安にする。詳しい背景は本文へ移し、タイトルだけに収めるために理由を削らない。
- 英語の識別子と日本語の間に半角スペースを入れない（例: `Userモデル`、`N+1クエリ`）。
- レビュープロセスに言及しない（「レビュー指摘の修正」「フィードバックを受けて」等は禁止。変更の動機を直接書く）。

### 本文の構成（最重要）

- 本文の中心は、変更が必要になった背景や要件と、判断の理由に置く。変更内容は理由とのつながりを理解するために必要な範囲で補う。文数は固定しない。タイトルで伝わる変更内容は繰り返さなくてよい。
- 変更種別に応じて、理由の焦点を合わせる。
  - 不具合修正: 期待する挙動と実際の挙動の差、および確認できた影響を書く。
  - 機能追加・要件対応: 実現する利用方法や要件を書く。
  - 設定変更・運用改善: 採用する運用方針、責務分担、構成上の目的を書く。
  - リファクタリング・保守改善: 維持したい挙動と、変更容易性や理解しやすさの目的を書く。
  - 文書・テスト整備: 明確にする仕様、固定する挙動、検証できるようにする範囲を書く。
- 「壊れていた」「誤っていた」「できなかった」「駄目だった」など、障害や誤りを示す表現は、不具合である根拠を確認できた場合だけ使う。
- 不具合でない変更を正当化するために、変更前の状態を欠陥として描写しない。方針の統一、責務の明確化、将来の変更容易性など、確認できた目的をそのまま書く。
- 変更内容を繰り返すだけの本文（「〜に変更した。」のみ等）を書いてはならない。本文がタイトルの言い換えになった場合は、理由の説明が足りているかを確認する。足りなければ理由を書き、既にタイトルで伝わっていれば本文を省く。
- 1段落は必ず1行で書き切る。散文の途中で改行しない。改行してよいのは箇条書き（`- `で始まる行）の間だけ。
- クラス名・メソッド名の列挙で本文を埋めない。列挙が必要ならパターンAの箇条書きに移す。

### パターン選択

**必要な理由と変更内容を確認してから、それが伝わる形式を選ぶ。** 特定のパターンを優先しない。ファイル数、変更行数、単一目的かどうか、直近の使用割合では決めない。

| パターン | 構成 | 使う条件 |
|---|---|---|
| A | タイトル+本文+箇条書き | 理由の説明に加え、個別に示す必要がある複数の要点がある場合 |
| B | タイトル+本文 | なぜ変更が必要だったかを伝えるために、背景、要件、制約や採用理由の説明が必要な場合 |
| C | タイトルのみ | タイトルだけで対象、変更内容、具体的な変更理由が伝わり、重要な背景や条件が失われない場合 |

提示前にメッセージだけを読み、読者が「なぜ必要だったか」を具体的に説明できるか確認する。手段や変更結果しか書かれていなければ理由を補う。理由を創作したり、短くするために重要な条件を落としたりしない。この確認の過程を長く出力する必要はない。

### 例

パターンA（複数の関連変更）:

```
ダイアログ操作のリダイレクトをturbo_stream応答に変更

turbo-frame内のダイアログフォームは成功時にリダイレクトすると、Turboが送信元フレームを遷移先に探すため表示が壊れていた。成功時はturbo_streamで一覧と詳細をまとめて更新し、Turbo以外のリクエストはリダイレクトにフォールバックするようにした。

- 共通のレスポンス処理をconcernに集約し、各コントローラを移行
- 各操作にas: :turbo_streamの振る舞いテストを追加
```

パターンB（バグ修正: 1文目が原因、2文目が対処）:

```
バリデーション失敗時のrenderに422ステータスを追加

Turbo Driveはフォーム送信に対する200応答を処理しないため、保存に失敗してもエラー画面が表示されず無反応になる不具合があった。Rails 7以降の標準に合わせてstatus: :unprocessable_entityを指定した。
```

パターンB（性能改善: 1文目が確認できた事実、2文目が対処）:

```
一覧画面のバッジ表示で関連レコードのN+1を解消

バッジの表示判定がhas_oneの存在確認であるにもかかわらず一覧クエリでpreloadされておらず、行数分のSELECTが発生していた。一覧表示と再描画の両経路のpreloadに関連を追加した。
```

パターンB（設定変更: 1文目が運用方針、2文目が対処）:

```
ECSデプロイ処理をBuildからDeployステージに変更

CodePipelineの標準ECS Deployアクションを使い、BuildとDeployの責務を分ける方針とした。Buildからタスク定義の登録とサービス更新を外し、Deployステージで実行する構成に変更した。
```

この例で「標準ECS Deployアクションを有効にしても直接更新を続ける状態だった」とだけ書くと、確認していない不具合や影響を連想させる。設定変更では、変更前の状態への否定的な評価ではなく、採用した方針と責務の移動を書く。

パターンC（タイトルだけで対象、変更内容、目的を説明し切れる変更）:

```
日付経過で期限切れになる開発seedをCURRENT_DATE基準に変更
```

NG例（この形を出力してはならない）:

```
ダイアログ操作の応答を修正

turbo_stream応答に変更した。
```

本文がタイトルを言い換えただけの1文で、なぜ変更が必要だったかが書かれていない。

## Japanese Self-Check（必須ゲート）

**照合表を出力せずに`git commit`を実行してはならない。** メッセージは`-m`で渡すためファイル書き込みのチェックが効かず、ここでの照合が唯一の検査になる。「確認した」という宣言だけでは完了と見なさない。

タイトルと本文を1行ずつ読み、以下の観点で照合する:

- 漢語接頭辞と名詞を組み合わせた造語 -> 「〜していない」「〜でない」に言い換える
- 助詞の省略 -> 「次の〜」「〜で検索」のように助詞を補う
- 既存の語彙にない業務用語の造語（プロジェクトで確立済みのドメイン用語は造語として扱わない）
- AGENTS.mdで禁止された語 -> 具体的なインターフェース、条件、挙動、要件に言い換える（プロジェクトで確立済みの用語も例外にしない）

続けてタイトルと本文を合わせて読み、文章全体を照合する。上の定型に該当しないことだけで問題なしと判断しない。

- 語や言い回しの反復が冗長なら文を組み直す。対比や意味の明確化に必要な反復は残す。
- 本文がタイトルの言い換えだけなら、Message Rulesに従ってWhyの不足を確認する。理由が不足していれば補い、タイトルだけで理由まで伝わる場合に本文を省く。
- 理由と行為が自然につながるか確認する。つながらない場合は欠けている問題や目的を確認し、単に2文へ分けたり、根拠のない理由を足したりしない。

出力形式（指摘ゼロでも表を出力し「指摘なし」と明記する）:

| 対象行 | 元の表現 | 判定 | 修正後 |
|--------|---------|------|--------|
| タイトル | （原文） | OK / 造語 / 助詞省略 / 禁止語 | （修正案。OKなら空欄） |
| 本文1行目 | （原文） | ... | ... |
| 全体 | （重複、Whyの不足、理由と行為のつながり） | OK / 問題と該当箇所 | （修正案。OKなら空欄） |

不自然な表現があれば修正し、修正後のメッセージでコミットする。

## Guardrails

- ユーザー許可なしにコミットしない。
- `git add .`、`git add -A`、`--no-verify` は使わない。
- pre-commit hookが失敗した場合は修正して再実行する。回避しない。
