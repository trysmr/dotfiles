# Pull Request Workflow

コミット済み変更に対してGitHub pull requestを作成する。

## Preconditions

- 変更がコミット済みであること。
- 必要なテストとlintが通っていること。
- ブランチがpush済み、またはpush許可を得られること。

## Workflow

1. `README.md` と `../_shared/branch-strategy.md` を必要に応じて確認する。
2. `git branch -a`、`git status`、`git log --oneline -5` で状態を確認する。
3. ベースブランチを決める。`hotfix/*` は `main`、その他は `staging` があれば `staging`、なければ `main`。
4. `git diff <base>...HEAD` でPR範囲の差分を確認する。
5. プロジェクトのテスト/lintコマンドを検出して実行する。`package.json`に`lint:css`や`test:js`がある場合も必ず実行する。失敗した場合はPR作成を止める。実行したことだけを理由にPR本文へ列挙せず、下記「テスト計画（最重要）」に従って変更と直接関係する検証を選ぶ。
6. 軽微な誤字修正と文書だけの変更を除き、PR案を作る前に別セッションの`change-reviewer`でPre-PRレビューを実行する。`change-reviewer`を利用できない場合は、別セッションの`deep-review`を使う。自分で差分を読み直すだけで代用しない。セキュリティ関連変更では`security-reviewer`も実行する。Critical/Highは先に修正し、Medium以下と残リスクもユーザーへ報告する。
7. 下記のPR Body Rulesに従ってタイトルと本文を作成する。
8. 日本語セルフチェックの照合表を出力する（必須ゲート。下記参照）。
9. PR情報をユーザーに提示して許可を得る。
10. 許可後、必要なら `git push -u origin <branch>` を実行し、下記の形式で`gh pr create`を単独実行してURLを提示する。
11. PR作成後、会話名をPRの番号とタイトルに合わせるため、次の指示を出す。
    `/rename <PRの番号>-<ブランチ名>`

## PR Body Rules

テンプレート:

```markdown
## 概要

[確認できた動機+何を変えたかを丁寧語で1〜3文。動機が提示されていなければ、依頼された変更内容から書く]

## 変更点

- `対象`: 変更内容

## テスト計画

- [x] RuboCop静的解析パス
- [x] 全テストN件パス(0 failures, 0 errors)
```

### タイトル

- 「何を/どう変えたか」を普通形・体言止めで1行、50文字以内。丁寧形・絵文字・接頭辞は使わない。
- 例: `一覧画面に担当者の絞り込みを追加` / `ダイアログ操作でContent missingになる不具合を修正` / `テスト実行時の警告とflakyテストを解消`

### 概要

- 丁寧語（です・ます）で1〜3文。動機が確認できる場合は「なぜ変えたか」を先に、「何を変えたか」を後に書く。
- 動機は依頼文、会話、Issueなどで明示された事実だけを書く。明示されていない困りごと、原因、要望、利用者の行動を推測して補わない。
- 動機が提示されていない場合は問題設定を作らず、依頼された変更内容をそのまま概要の起点にする。
- バグ修正は原因と修正の両方を書く。
- 本筋に付随する小さな変更は「また、〜」「あわせて〜」で1文追加する。別セクションを立てない。
- 「確認できた動機（なければ依頼された変更） -> 何を変えたか -> 必要な補足」の順で書く。
- 概要の最初を「〜を改善しました」のような抽象的な表現だけで済ませない。「どの画面で何を確認できないか」「どの操作で何が起きるか」を具体的に書く。
- 実装方式より、画面や機能の利用者から見て何が変わるかを優先する。原因の説明に必要な場合だけ実装方式を書く。
- 複数の変更を無理に一つの原因へまとめない。関連する変更は「また、〜」「あわせて〜」で自然につなぐ。
- 名詞を積み重ねず、一文が長ければ分割する。積み重なった名詞は動詞や助詞でほぐす（「不変な設定入力を追加」->「設定に渡す不変な入力を追加」）。
- スキル内の例文は公開リポジトリへ保存される前提で汎用化し、組織名、システム名、実在の画面名、業務固有の用語、実在PRの番号・URL・本文を含めない。

基準例（利用者の困りごと、対応、補足の順で書く）:

```markdown
## 概要

一覧では必要な更新情報を確認できず、対象を探すために各詳細を開く必要がありました。一覧に更新日時を追加し、新しい順を初期表示として昇降順に切り替えられるようにしました。補助情報を持つ一覧では、その情報が最後に更新された日時を表示します。
```

例（バグ修正: 1文目が原因と症状、2文目が修正内容）:

```markdown
## 概要

ダイアログ操作は、turbo-frame内のフォーム送信に対しリダイレクトで応答していたため、送信元フレームが消えて「Content missing」になっていました。成功時をturbo_stream応答に変更し、トーストと一覧・詳細をまとめて更新するよう修正しました。あわせて、各テンプレートに重複していたturbo_streamブロックを共有パーシャルに集約しました。
```

### 変更点

- 1項目1行。`` `対象`: 変更内容 `` の形式で書く。対象は原則ファイルパスで書き、クラス名や概念のまとまりで代替しない。同一ディレクトリの複数ファイルは`/`でまとめる（テーブル名はスキーマ変更などファイルより対象が明確な場合のみ）。
- diffの全ファイルを書き写さず、意味のあるまとまり単位で書く。テスト追加は1行にまとめてよい。
- スコープ外の項目がある場合は `### 対象外（別PR/別フェーズ）` サブセクションに書く。

### テスト計画（最重要）

次の2行を**基本形**とする。両方を実行して成功した場合は、必ずこの順で出力し、`N`を全テストの実測件数に置き換える。

```markdown
## テスト計画

- [x] RuboCop静的解析パス
- [x] 全テストN件パス(0 failures, 0 errors)
```

- **実際に実行して通った検証だけ**を `- [x]` で書く。実行していない検証を書いてはならない。
- 基本形の後には、**変更内容と直接関係し、実行して成功した検証だけ**を追加する。コマンドが存在することや実行したことだけでは掲載理由にならない。
- CSS変更がある場合のCSS lintは `- [x] CSS lintパス`、JavaScript変更がある場合のJavaScriptテストは `- [x] JavaScriptテストN件パス(0 failures, 0 errors)` とする。両方が変更と直接関係する場合はCSS lint、JavaScriptテストの順に続ける。
- **ユーザーが基本形と異なる項目・順序・文言を指定した場合は、その指定をテスト計画の出力要件として最優先する。** 指定された行だけを、指定された順序と文言で書く。実測が必要な件数だけは実行結果で置き換える。
- **プロジェクトに存在し、PR差分と直接関係するチェックだけ**を書く。`package.json`に`lint:css`や`test:js`が存在しても、対象領域を変更していなければそれぞれの結果行を書かない。
- テスト結果は実測値で書く: `全テスト2506件パス(0 failures, 0 errors)` / `対象コントローラ・モデルテスト76件パス(0 failures, 0 errors)`。件数のない「テストパス」は書かない。
- マージ後の環境でしか実施できない確認（staging動作確認など）は、ユーザーが明示した場合に限り `- [ ]` 未チェックで追加してよい。
- 手元での一回きりの手動確認（ブラウザ確認、one-offスクリプト）はテスト計画に入れない。記録する価値があれば概要に書く。

良い例（ユーザーがスコープを絞ったテスト計画を指定したPR）:

```markdown
## テスト計画

- [x] RuboCop静的解析パス
- [x] 対象コントローラ・モデルテスト76件パス(0 failures, 0 errors)
```

良い例（CSSとJavaScriptを変更し、基本形に関連する検証を追加したPR）:

```markdown
## テスト計画

- [x] RuboCop静的解析パス
- [x] 全テスト2489件パス(0 failures, 0 errors)
- [x] CSS lintパス
- [x] JavaScriptテスト8件パス(0 failures, 0 errors)
```

良い例（マージ後のstaging確認が必要なPR）:

```markdown
## テスト計画

- [x] RuboCop静的解析パス
- [x] 全テスト2489件パス(0 failures, 0 errors)
- [ ] staging環境でダイアログ操作がエラーなく完了することを確認
```

NG例（この形を出力してはならない）:

```markdown
## テスト計画

- [x] RuboCop静的解析パス
- [x] stylelint静的解析パス
- [x] 全テストパス
- [x] JSテストパス
```

実行していないCSS lint・JavaScriptテストの行があり、全テストの件数も実測値でない。実行していない検証にチェックを付けるのは虚偽報告になる。

本文を提示する直前に、テスト計画を基本形またはユーザー指定と機械的に照合する。指定外の行、順序変更、言い換えが1つでもあれば、指定どおりに直してから提示する。

## Japanese Self-Check（必須ゲート）

**照合表を出力せずに`gh pr create`を実行してはならない。** PR本文は`--body`で渡すためファイル書き込みのチェックが効かず、ここでの照合が唯一の検査になる。「確認した」という宣言だけでは完了と見なさない。

タイトルと本文を1行ずつ読み、以下の観点で照合する:

- 漢語接頭辞の造語（未〜/非〜と名詞の合成。例: 未充足、非終端）-> 「〜していない」「終端でない」に言い換える
- 助詞の省略（例: 「次エッジ」->「次のエッジ」、「LIKE検索」->「LIKEで検索」）
- 既存の語彙にない業務用語の造語（プロジェクトで確立済みのドメイン用語は造語として扱わない）
- 禁止語の「契約」「述語」 -> 具体的なインターフェース、条件、挙動、要件に言い換える（「API契約」やプロジェクトで確立済みの用語も例外にしない）

出力形式（指摘ゼロでも表を出力し「指摘なし」と明記する）:

| 対象行   | 元の表現 | 判定                          | 修正後                 |
| -------- | -------- | ----------------------------- | ---------------------- |
| タイトル | （原文） | OK / 造語 / 助詞省略 / 禁止語 | （修正案。OKなら空欄） |
| 概要     | （原文） | ...                           | ...                    |

不自然な表現があれば修正し、修正後の内容でユーザーに提示する。

## PR作成コマンド

PR本文はヒアドキュメントで`--body`へ渡す。`gh pr create`を`&&`、`;`、パイプ、引用外の改行で他のコマンドと連結しない。

```bash
gh pr create --base <base> --head <branch> --title "タイトル" --body "$(cat <<'EOF'
## 概要
...
EOF
)"
```

## Guardrails

- ユーザー許可なしにPRを作成しない。
- test/lint失敗中はPRを作成しない。
- Pre-PRレビューの内容をユーザーが判断できるように提示する。
- Critical/Highレビュー指摘がある場合は修正するかどうかの指示をユーザーに仰ぐ。
- `gh pr create`がTLS/証明書エラーで失敗した場合は`dangerouslyDisableSandbox: true`を指定して再実行する。
- PR URLとrename指示を必ず併記する。
