# Pull Request Workflow

コミット済み変更に対してGitHub pull requestを作成する。

## Preconditions

- 変更がコミット済みであること。
- 必要なテストとlintが通っていること。
- ブランチがpush済み、またはpush許可を得られること。

## Workflow

1. `README.md` と `../_shared/branch-strategy.md` を必要に応じて確認する。
2. `git branch -a`、`git status`、`git log --oneline -5` で状態を確認する。
3. ベースブランチを決める。`hotfix/*` は `main`、その他は `staging` があれば `staging`、なければ `main`。
4. `git diff <base>...HEAD` でPR範囲の差分を確認する。
5. プロジェクトのテスト/lintコマンドを検出して実行する。`package.json`に`lint:css`や`test:js`がある場合も必ず実行する。失敗した場合はPR作成を止める。
6. 可能なら `change-reviewer`、セキュリティ関連変更なら `security-reviewer` でレビューする。
7. 下記のPR Body Rulesに従ってタイトルと本文を作成する。
8. 日本語セルフチェックの照合表を出力する（必須ゲート。下記参照）。
9. PR情報をユーザーに提示して許可を得る。
10. 許可後、必要なら `git push -u origin <branch>` を実行し、`gh pr create` でPRを作成してURLを提示する。

## PR Body Rules

テンプレート:

```markdown
## 概要
[なぜ変えたか+何を変えたかを丁寧語で1〜3文]

## 変更点
- `対象`: 変更内容

## テスト計画
- [x] [実際に実行して通った検証のみ]
```

### タイトル

- 「何を/どう変えたか」を普通形・体言止めで1行、50文字以内。丁寧形・絵文字・接頭辞は使わない。
- 例: `一覧画面に担当者の絞り込みを追加` / `ダイアログ操作でContent missingになる不具合を修正` / `テスト実行時の警告とflakyテストを解消`

### 概要

- 丁寧語（です・ます）で1〜3文。「なぜ変えたか」を先に、「何を変えたか」を後に書く。
- バグ修正は原因と修正の両方を書く。
- 本筋に付随する小さな変更は「また、〜」「あわせて〜」で1文追加する。別セクションを立てない。

例（バグ修正: 1文目が原因と症状、2文目が修正内容）:

```markdown
## 概要
ダイアログ操作は、turbo-frame内のフォーム送信に対しリダイレクトで応答していたため、送信元フレームが消えて「Content missing」になっていました。成功時をturbo_stream応答に変更し、トーストと一覧・詳細をまとめて更新するよう修正しました。あわせて、各テンプレートに重複していたturbo_streamブロックを共有パーシャルに集約しました。
```

### 変更点

- 1項目1行。`` `対象`: 変更内容 `` の形式で書く。対象はファイルパス・クラス名・テーブル名のいずれでもよい。
- diffの全ファイルを書き写さず、意味のあるまとまり単位で書く。テスト追加は1行にまとめてよい。
- スコープ外の項目がある場合は `### 対象外（別PR/別フェーズ）` サブセクションに書く。

### テスト計画（最重要）

テンプレートの項目を埋めることが目的ではない。**実行していない2行を書くより、実行した1行だけを書くほうが正しい。**

- **実際に実行して通った検証だけ**を `- [x]` で書く。実行していない検証を書いてはならない。
- **プロジェクトに存在するチェックだけ**を書く。`package.json`に`lint:css`がないのにstylelintの行を書かない。JS変更がないのにJSテストの行を書かない。
- テスト結果は実測値で書く: `全テスト2506件パス(0 failures, 0 errors)` / `対象コントローラ・モデルテスト76件パス(0 failures, 0 errors)`。件数のない「テストパス」は書かない。
- マージ後の環境でしか実施できない確認（staging動作確認など）に限り `- [ ]` 未チェックで書いてよい。
- 手元での一回きりの手動確認（ブラウザ確認、one-offスクリプト）はテスト計画に入れない。記録する価値があれば概要に書く。

良い例（Ruby変更のみ、スコープを絞ってテストしたPR）:

```markdown
## テスト計画
- [x] RuboCop静的解析パス
- [x] 対象コントローラ・モデルテスト76件パス(0 failures, 0 errors)
```

良い例（マージ後のstaging確認が必要なPR）:

```markdown
## テスト計画
- [x] RuboCop静的解析パス
- [x] 全テスト2489件パス(0 failures, 0 errors)
- [ ] staging環境でダイアログ操作がエラーなく完了することを確認
```

NG例（この形を出力してはならない）:

```markdown
## テスト計画
- [x] RuboCop静的解析パス
- [x] stylelint静的解析パス
- [x] 全テストパス
- [x] JSテストパス
```

CSS/JS変更がないのにstylelint・JSテストの行があり、テスト件数の実測値もない。実行していない検証にチェックを付けるのは虚偽報告になる。

## Japanese Self-Check（必須ゲート）

**照合表を出力せずに`gh pr create`を実行してはならない。** PR本文は`--body`で渡すためファイル書き込みのチェックが効かず、ここでの照合が唯一の検査になる。「確認した」という宣言だけでは完了と見なさない。

タイトルと本文を1行ずつ読み、以下の観点で照合する:

- 漢語接頭辞の造語（未〜/非〜と名詞の合成。例: 未充足、非終端）-> 「〜していない」「終端でない」に言い換える
- 助詞の省略（例: 「次エッジ」->「次のエッジ」、「LIKE検索」->「LIKEで検索」）
- 既存の語彙にない業務用語の造語（プロジェクトで確立済みのドメイン用語は造語として扱わない）

出力形式（指摘ゼロでも表を出力し「指摘なし」と明記する）:

| 対象行 | 元の表現 | 判定 | 修正後 |
|--------|---------|------|--------|
| タイトル | （原文） | OK / 造語 / 助詞省略 | （修正案。OKなら空欄） |
| 概要 | （原文） | ... | ... |

不自然な表現があれば修正し、修正後の内容でユーザーに提示する。

## Guardrails

- ユーザー許可なしにPRを作成しない。
- test/lint失敗中はPRを作成しない。
- Critical/Highレビュー指摘がある場合は先に修正する。
- `gh pr create`がTLS/証明書エラーで失敗した場合は`dangerouslyDisableSandbox: true`を指定して再実行する。
