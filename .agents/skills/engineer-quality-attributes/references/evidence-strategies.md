# 証拠の組み立て方

品質を支える情報を、期待の定義、対策、試験結果、実際の観測、基準外への対応へ分ける。

## 5段階の証拠

| 段階 | 確認する内容 | 証拠例 | 単独では言えないこと |
|---|---|---|---|
| 要件 | 期待する応答、測定基準、条件、担当が定義されている | 品質シナリオ、受入条件、判断記録 | 実装や運用で実現していること |
| 対策 | 失敗の予防、検知、軽減、回復を設計または設定している | コード、構成、権限制御、冗長化、設計記録 | 対策が意図どおり動くこと |
| 検証 | 定義した条件で期待する結果を確認した | 自動テスト、負荷試験、障害試験、手動評価の結果 | 実環境で継続して保たれること |
| 観測 | 実環境または本番相当環境の振る舞いを測っている | メトリクス、ログ、トレース、利用者調査、監査結果 | 基準外へ対応できること |
| 対応 | 基準を外れた事象を通知し、判断し、復旧・改善する | アラート、当番、手順、訓練記録、事後分析 | 再発防止が有効であること |

各段階を`あり`、`一部`、`なし`、`確認できない`で評価し、ファイル、行、テスト名、ダッシュボード名、文書名などの位置を添える。

## 証拠の強さ

同じ種類でも強さが異なる。次の順序を機械的な点数にせず、対象のリスクと照らして評価する。

- 記述: 方針や意図が書かれている
- 実装: コードや設定として存在する
- 実行結果: 定義した条件で試し、結果を保存している
- 継続観測: 期間、母集団、環境を明示して測っている
- 対応実績: 基準外を検知し、手順を実行して改善を確認している

次を根拠に品質を満たすとは断定しない。

- 文書に目標だけが書かれている
- Terraformや設定ファイルに対策が宣言されている
- テストコードが存在するが、実行結果を確認できない
- ダッシュボードが存在するが、測定定義と基準がない
- アラートが存在するが、通知先と対応手順がない

## 確認方法の使い分け

### アプリケーションテスト

適する内容:

- 業務結果、計算、状態遷移、権限別の振る舞い
- 入力境界、例外、再試行、重複実行
- 外部連携の形式とエラー処理

限界:

- 本番の負荷、依存先、ネットワーク、利用者行動は再現範囲に限りがある。
- mockだけでは実接続の相互運用性を確認できない。

### 静的解析と構成確認

適する内容:

- 既知の危険な書き方、依存物、公開範囲、暗号化設定
- 命名、複雑さ、重複、構成上の必須条件
- Infrastructure as Codeの入力、生成予定の資源、組織共通ルール

限界:

- 実行時の経路、実際の権限、負荷時の挙動、復旧結果を直接確認しない。
- 警告が真の問題か、対象外かを文脈と照合する必要がある。

### 負荷・容量試験

適する内容:

- 応答時間の分布、処理量、資源使用量、上限、劣化の仕方
- 自動拡張、キュー、接続プール、外部制限の影響

限界:

- 代表的なデータ量、利用パターン、依存先を再現できなければ結果を一般化できない。
- 本番より小さい環境の値を、そのまま本番目標へ使わない。

### 障害・復旧試験

適する内容:

- 障害検知、切替、縮退、再試行、隔離、バックアップ復元
- 復旧時間、失われるデータ、復旧後の整合性

限界:

- 冗長化設定や手順書の存在だけでは復旧結果を確認できない。
- 本番へ影響する試験は範囲、費用、戻し方、明確な許可を先に確認する。

### 監視・SLI・SLO

適する内容:

- 実際の可用性、待ち時間、失敗、資源、依存先、利用量
- 時間帯や利用者群ごとの傾向、基準外の検知

限界:

- 計測漏れ、サンプリング、集計窓、ラベル設計で見え方が変わる。
- SLOの値には業務上の根拠が必要であり、現在値から自動生成しない。

### 利用者による評価

適する内容:

- タスク達成、理解、学習、誤操作、支援技術、満足、信頼、受容
- 実際の利用状況での便益と悪影響

限界:

- 対象者、タスク、環境、人数、収集方法を示さない結果は一般化しない。
- 自動アクセシビリティ確認だけで、対象利用者の利用可能性を断定しない。

## 特性ごとの組み合わせ

| 特性 | 主な検証 | 主な観測 | 補足 |
|---|---|---|---|
| 機能適合性 | 業務例、回帰テスト、照合 | 業務エラー、差異、問い合わせ | 仕様とテストの一致を確認する |
| 性能効率性 | 負荷・容量試験 | 応答分布、処理量、資源 | 条件と集計方法を固定する |
| 互換性 | 結合試験、相手との適合確認 | 連携成功率、形式エラー | 設定だけで完了にしない |
| インタラクション能力 | 操作評価、アクセシビリティ確認 | 完了率、誤操作、支援依頼 | 対象利用者を明示する |
| 信頼性 | 障害・復旧試験 | 可用性、失敗、復旧時間 | 復旧後のデータも照合する |
| セキュリティ | 認証・認可テスト、解析、攻撃試験 | 不正試行、変更、追跡記録 | 詳細は専門reviewへつなぐ |
| 保守性 | 単体・結合テスト、変更影響の確認 | 変更所要、回帰、障害原因 | 数値だけで設計品質を断定しない |
| 柔軟性 | 複数構成、拡張、導入、置換試験 | 拡張時間、導入失敗、上限 | データ移行も含める |
| 安全性 | 危害分析、フェイルセーフ試験 | 危険状態、警告、事故・寸前事例 | 人と業務への結果を確認する |
| 利用時品質 | 利用状況ごとのタスク・リスク評価 | 便益、損失、満足、受容 | 製品品質と別表にする |

## 既存実装を評価する手順

1. リポジトリの安全規則と評価範囲を確認する。
2. `.env`、credentials、Terraformのstateや保存済みplan、Gitで除外されるファイルを許可なく読まない。
3. 要件、中心となるコード、構成、テスト、CI、監視設定、運用文書の順に位置を探す。
4. 9特性をすべて分類し、関連する証拠の位置を記録する。
5. 各シナリオを5段階へ対応付け、存在、実行結果、鮮度、対象環境を確認する。
6. 確認した事実、そこから導く推測、担当者の判断が必要な項目を分ける。
7. 不足をリスク順に並べ、最小の次の確認または改善を示す。

コマンドを実行する前に、副作用、外部接続、資格情報、費用、対象環境を確認する。読み取りだけの調査依頼では、外部システムへの変更を行わない。

## 不足の報告方法

不足を「テストがない」だけで終わらせず、次を示す。

| 項目 | 内容 |
|---|---|
| 対象シナリオ | どの期待と条件に関する不足か |
| 不足段階 | 要件、対策、検証、観測、対応のどこか |
| 確認した事実 | 読んだファイル、実行結果、確認できた設定 |
| 推測 | 事実から推定する影響。推測と明示する |
| リスク | 何を誤判定または見落とす可能性があるか |
| 次の確認 | 最小の追加調査、試験、担当者への質問 |
| 担当 | 判断または作業を引き受ける役割 |

証拠を確認できない場合は`品質を満たさない`と即断せず、`確認できる証拠が不足している`と報告する。ただし、明示した必須条件に反する事実がある場合は、その不適合を具体的に示す。
